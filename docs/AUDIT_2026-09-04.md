## Group A — Blocks Phase 8 on the first run

### A1. The four-way policy comparison is structurally guaranteed to tie
**Status: partially fixed (see A1-a). The core coupling gap remains open.**

Three independent mechanisms each force a tie; any one alone is sufficient.

**A1-a — the intervention library collapsed to one item. FIXED 2026-09-04.**
`select_best_intervention` fixes `magnitude = max_magnitude / 2`, which makes the risk term
`(magnitude / max_magnitude) * RISK_SCALE` a constant 2.50 for all four interventions:

```
intervention            mag    cost    risk  cost+risk
curtailment            0.15    0.75    2.50       3.25
high_res_sampling      2.00    1.00    2.50       3.50
setpoint_change        0.05    0.10    2.50       2.60   <- always won
high_res_logging       4.50    0.90    2.50       3.40
```

Information value depends only on the node, so the argmax over interventions was always the
lowest `cost_fn(max/2)`. Swept over reduction 0.001–0.9 × node degree 1–5, the set of
interventions ever selected was `{None, 'setpoint_change'}`.

Fixed by `target_var` (see A1-b): each intervention now declares the variable it manipulates,
and the four declared targets are distinct, so each node has exactly one compatible
intervention. The magnitude is still pinned at `max/2` — a magnitude *search* remains open
work (Phase 5).

**A1-b — the selected intervention was a no-op, and mis-targeted. FIXED 2026-09-04.**
`_apply_setpoint` writes `power_factor`, which nothing outside `library.py` reads. Worse, the
probe node and the manipulated variable were decoupled entirely — measured:

```
probe node   : poa_irradiance
intervention : setpoint_change (magnitude 0.05)
what apply() actually manipulates: {'power_factor': (None, 0.95)}
```

`update_graph_with_intervention` was then told irradiance had been intervened on, and severed
its incoming edges on that basis — Pearl's mutilated graph applied to an intervention that
never happened. You cannot intervene on irradiance; it is the sun.

Fixed: `INTERVENTIONS[name]["target_var"]` declares what each intervention writes, a test
asserts the declaration matches what `apply()` actually changes, and
`select_best_intervention` only pairs a node with interventions that can reach it.

**A1-c — no channel from causal knowledge to allocation. OPEN — this is Phase 2.**
`solve_slot` takes no graph and no world model. A better causal graph cannot produce a better
allocation even in principle. Until this exists, active ≡ passive ≡ observational_only ≡
oracle on every operational metric, and §11's headline claim has no mechanism by which it
could come out either true or false.

### A2. The Tier-2 fleet graph cannot be fit — four of six variables do not exist
**Status: OPEN.**

```
site_timeline columns: timestamp, power_mw, plant_id, kind, hour_of_day,
                       sim_day_solar, sim_day_cluster, cpu_rate_sum, site_id
Tier-2 var_names MISSING: curtailment_frac, sampling_rate_hz, cost, risk
fit_observational_graph(...) -> KeyError
NODE_SCHEMA names present in the fleet timeline: 2 of 11
```

Synthesising them does not fix it: `curtailment_frac` and `sampling_rate_hz` are **constant**
unless the engine writes them back, and a constant column can never appear in a discovered
graph. The actuators the orchestrator controls are causally invisible to the graph meant to
tell it what to actuate.

### A3. Interface drift — the plan's `run_policy` cannot call `ActiveOrchestrator`
**Status: OPEN (decide before writing Phase 7).**

The plan's self-review claims an identical `.step(site_states, graph, uncertainty_estimates)`
across all orchestrators. Actual signature is
`.step(site_states, world_model, df, graph, node_candidates, var_names, tau_max=1)`, and the
plan's call raises `TypeError: unexpected keyword argument 'uncertainty_estimates'`.

### A4. The plan's Task 8.2 fixture uses the removed `sim_day` column
**Status: OPEN (plan text only).** `ReplayEngine(...)` on that fixture raises
`KeyError: 'sim_day_solar'`. Same bug class Phase 1.5 already fixed inside `engine.py`; it
simply survived in the plan downstream.

## Group B — Data integrity

### B1. The Google trace on disk is 25 hours, not 29 days, and it stamps a day-parity artifact through the fleet timeline
**Status: OPEN. Highest-priority data fix.**

```
google_cluster_2011/{job,task}_events, task_usage:
  part-00200-of-00500 .. part-00217-of-00500        (18 of 500, 3.6%)
machine_utilization_5min.parquet wall_time:
  2011-05-13 09:20  ->  2011-05-14 10:25            (25.1 hours)
=> build_site_timeline: cluster_days = [0, 1]
   sim_day_cluster = cluster_days[sim_day_solar % 2]
```

The inner merge on `(sim_day_cluster, hour_of_day)` drops every solar slot whose hour is
absent from the cluster day it was assigned:

| solar day parity | hours covered | slots/day | mean power |
|---|---|---|---|
| even | 09:20 – 23:55 | 176 | **28.745 MW** |
| odd | 00:00 – 10:25 | 126 | **10.156 MW** |

55,140 of a possible 105,120 per-site slots survive — **52.5%** — and available fleet power
oscillates ~3× between consecutive simulated days for a purely artifactual reason, with each
parity sampling a disjoint half of the diurnal cycle. Every Phase 8 time series will carry a
strong period-2 component that is the join, not physics and not policy.

**Recommended fix:** given only ~25 h exist, collapse them into a single 24-hour diurnal
`cpu_rate_sum` profile over `hour_of_day` and join every solar day to that. Honest about there
being one day of cluster variability, and restores 100 % slot coverage. Alternative: download
the remaining 482 shards.

### B2. The fleet graph's strongest discovered edge is an artifact of the same join
**Status: OPEN.** Tier-2 fit on 500 real ticks, `tau_max=3`:

```
('power_mw', 'cpu_rate_sum', pval=0.0,     lag=0)
('cpu_rate_sum', 'cost',      pval=0.00117, lag=1)
```

A 2006 Arizona PV plant does not cause CPU load in a 2011 Google datacentre. The edge exists
because `build_site_timeline` joins the two on `hour_of_day`, so both carry the same diurnal
cycle — confounding by the alignment variable. Best turned into an asset: a known-confounded
pair the method is *expected* to reject is a legitimate negative control.

### B3. `module_temp` is never materialised
**Status: OPEN.** `NODE_SCHEMA` names one `module_temp`; `system_51_weather.parquet` has only
`module_temp_1/2/3`, kept deliberately distinct by `CORE_COLUMNS`.
`run_voi_proxy_check.py` averages them privately in its own `main()`, so every future Tier-1
consumer must remember to repeat it. Belongs in the ingest.

### B4. Physically impossible negative sensor values survive cleaning
**Status: OPEN. Affects existing published results.**

`-99999.0` is not the only sentinel. Undocumented values found: `-7999`, `-5308.9`,
`-50001.8`, `-53999`.

```
system    n_nonnull   n_negative    pct        min
10        6,425,526      106,388   1.7%    -5308.9
1283     14,006,462       83,289   0.6%    -7999.0
4         5,812,228      146,544   2.5%    -7999.0
50        2,887,624    1,394,876  48.3%   -53999.0
51        3,162,550       11,180   0.4%   -50001.8
```

`run_voi_proxy_check.py` and `run_clipping_validation.py` both use system_51 and only
`dropna()`, so 11,180 impossible rows feed the existing VoI and clipping results.

### B5. system_50 is worse than documented; system_1283 has a sign flip
**Status: OPEN.** Phase 1.5 records system_50's post-2015 collapse as inverter failure. The
*irradiance sensor* is also dead: 48.3 % negative, and ≈ −0.1 correlation with every
neighbouring system's POA. It should be excluded entirely after 2014, not merely from
calibration. Separately, `corr(poa_irradiance, dc_power)` for system_1283 is **negative**
(−0.61 … −0.40) for 2012–2017 then +0.954 in 2018 — consistent with a wiring or sign change;
only 2018 is usable.

## Group C — Method gaps a reviewer will find

### C1. CVaR is computed over a single scenario
**Status: OPEN.** Both `orchestrator.py` and the plan's `run_policy` build
`risk_samples = [[...]]` with `n_samples = 1`. Rockafellar–Uryasev then collapses to that
scenario's own value — a deterministic linear constraint wearing a CVaR name:

```
cvar_limit=0.5   alloc=5.0000  cvar=0.5000   == 0.1 x alloc exactly
cvar_limit=0.1   alloc=1.0000  cvar=0.1000   == 0.1 x alloc exactly
```

The plan's `run_policy` compounds it by hardcoding `cost_per_unit: 1.0` and
`risk_sample: [0.1]`, identical across every site and tick. Note this is a *larger* gap than
the already-disclosed empirical-CVaR-instead-of-Wasserstein simplification, which concerns the
ambiguity set's shape rather than its existence.

### C2. The Lyapunov `V` knob has a hard cliff at `DEMAND_FULFILLMENT_VALUE / cost_per_unit`
**Status: OPEN.** Measured through `solve_slot` exactly as `ActiveOrchestrator` calls it
(`cost = cost_per_unit * V`, `cost_per_unit = 1.0`, demand 6, budget 10):

```
V=1 .. V=999   allocation = 6.0000   status=optimal
V=1000         allocation = 4.9762   status=optimal
V=1001, 5000   allocation = 0.0000   status=optimal
```

Once `cost_per_unit * V` exceeds `DEMAND_FULFILLMENT_VALUE = 1000` the net objective flips
sign and allocating nothing becomes optimal. Sweeping `V` over orders of magnitude to show the
standard O(1/V) / O(V) utility–queue trade-off is exactly what a Lyapunov paper does, and here
that sweep falls off a cliff. The two constants are coupled and nothing documents it.

### C3. The virtual queue is decorative — for two reasons
**Status: OPEN.** `PROJECT_OVERVIEW.md` already records that a hard per-slot CVaR constraint
means the queue can never register a soft violation (confirmed: pinned at 0.0 across slots).
Separately, `self._queue` is **never read back** into `select_best_intervention` or
`solve_slot`. Drift-plus-penalty is defined by the queue weighting the objective; here it is a
write-only counter. Both halves need fixing.

### C4. No counterfactual method — and it is on the critical path
**Status: OPEN — Phase 3 of the roadmap.** `CausalWorldModel` exposes `fit`, `predict`, `do`,
`estimate_uncertainty_reduction`. §6.3 requires interventional *and* counterfactual
("what would have happened under a different allocation"). Task 4.2's report defers the twin's
real validation to "Phase 8's counterfactual prediction accuracy", which cannot be computed
without it. With the clipping natural experiment confirmed absent, the twin currently has
**no** completed validation of causal fidelity.

### C5. No multiple-testing correction on the discovered edge set
**Status: OPEN.** `fit_observational_graph` uses `pc_alpha=0.05` then a raw `p < 0.05` edge
threshold. Across 11 variables and `tau_max=3` that is several hundred hypothesis tests per
fit with no FDR control — and "reduction in causal edge uncertainty" is a headline metric.

### C6. `tau_max` is inconsistent between fitting and probing
**Status: OPEN.** Graph fits default to `tau_max=3`; `estimate_uncertainty_reduction`,
`select_best_intervention` and `ActiveOrchestrator.step` all default to `tau_max=1`. A lag-2
or lag-3 edge can exist in the graph while being invisible to the probe meant to sharpen it —
a silent, direction-consistent underestimate of information gain.

### C7. The uncertainty-reduction signal is a cliff, not a gradient
**Status: OPEN — resolve as part of Phase 2.** Measured on the standard test fixture:

```
rows=300  reduction=1.0000  score=+2.4000  -> INTERVENE
rows=301  reduction=0.0199  score=-2.5005  -> skip
rows=303  reduction=0.0000  score=-2.6000  -> skip
```

`_avg_pval` returns a default of `1.0` when no edge touches the node, so "maximum information
gain" is a constant standing in for "the pre-fit found nothing," not a measurement. Phase 2
feeds causal uncertainty into the ambiguity set; a step-function input yields a step-function
risk signal.

## Group D — Runtime and process

### D1. VoI scoring cost
**Status: mitigated 2026-09-04.** `select_best_intervention` measured **3.01 s per slot**
(6 candidate nodes × 4 interventions × 2 PCMCI+ fits, 500-tick fleet window, `tau_max=1`),
which put the plan's `n_ticks=2000` at ~1.7 h for the active policy and the full 55,140-tick
timeline at ~46 h. The three baselines never call it.

Mitigated by one-intervention-at-a-time: selection now runs once per duty cycle rather than
every slot — measured 3 evaluations in 12 slots at `min_post_obs=5`, a factor of
`min_post_obs + 1` fewer calls.

### D2. `ReplayEngine` clamps at the last row instead of signalling exhaustion
**Status: OPEN.** `step()` advances with `min(cursor + 1, len - 1)`, so an over-run silently
replays the final tick forever with no `done` flag. 55,140 ticks are available, so
`n_ticks=2000` is safe today, but nothing guards it.

### D3. Branch hygiene
**Status: OPEN.** Phases 5–6 were developed on `fix-task-4.2-validation` (6 commits ahead of
`main`, 0 behind), a branch named for a Task 4.2 bugfix. Phase 1 loop-closure work is on
`feat/close-causal-loop`. Merge to `main` before Phase 7 branches off.

### E1. The intervention lasts one slot; its observation window lasts the whole cycle
**Status: OPEN — next work item (Phase 1.1).** Measured over 12 slots at `min_post_obs=5`:

```
slots where the fleet was actually curtailed : [0, 5, 10]
window passed to update_graph_with_intervention : 5 observations
  of which taken while the intervention was live : 1
```

At the realistic `min_post_obs=120` this is 1 interventional row in 120 (<1 %). §8.4's update
remains defensible — data following an intervention is reasonably "the resulting observational
data". But §6.1's *identification* claim is not: the mutilated-graph severing asserts edges
into `target_var` cannot be real *because we set that variable*, which holds only while it is
clamped. Applying it to a 99 %-unclamped window is the same category of error as the
`poa_irradiance`/`power_factor` mispairing fixed in A1-b.

**Fix:** hold the intervention across the observation window (`apply_intervention` each slot
while pending; `result["intervention"]` stays non-None so a runner keeps feeding it to the
engine). This also gives §8.1's "limited-duration" a real parameter — and forces a cost-model
correction, since `cost_fn(magnitude)` is a one-shot charge while a curtailment held 120 ticks
is 10 hours of lost generation that §6.2 must weigh against the information gain.

### E2. VoI is no longer evaluated at every decision epoch
**Status: deliberate deviation — record in the paper.** One-intervention-at-a-time means VoI
is evaluated once per cycle. Either redefine "decision epoch" as the cycle, or evaluate every
slot and decline to act while pending.

## Group F — Data scope: could the whole project use real data only?

The fleet tier uses NREL Solar Power Data for Integration Studies, which the proposal itself
(§9.1) and the plan's Current State table both identify as **simulated plants** — model
output, not sensor measurement. `PROJECT_OVERVIEW.md` and Phase 1.5 nevertheless described it
as "the fleet's real metered output"; that phrasing is wrong and is corrected.

**Could PVDAQ alone carry both tiers?** More than Phase 1.5 assumes. All five systems have the
physical variables, and they overlap heavily in real calendar time — a multi-system panel
would need **no simulation clock at all**:

```
year      sys_10   sys_4   sys_50   sys_51   sys_1283
2012       0.989   0.987    0.980    0.980     -0.609
2014       0.977   0.957    0.902    0.950     -0.550
2018       0.991   0.961    0.042    0.979      0.954
2021       0.991   0.989    0.032    0.922        -
```
(`corr(poa_irradiance, dc_power)`; 2012 and 2014 give four systems above 0.90 on a shared
real calendar.)

**But it fails on spatial diversity.** Cross-system POA irradiance correlation, 2018, hourly:

```
        10    1283      4      50      51
10   1.000   0.824  0.982  -0.101   0.953
1283 0.824   1.000  0.799  -0.102   0.775
4    0.982   0.799  1.000  -0.079   0.972
51   0.953   0.775  0.972  -0.090   1.000
```

Systems 10, 4 and 51 see **the same sky** (0.95–0.98). 1283 is a genuinely different location
(≈0.8). 50 is broken. Real data therefore gives **two distinct skies, not twenty sites** —
ramp propagation across a fleet and cross-site orchestration are not testable on two
locations. This, not variable availability, is the real justification for Tier 2, and it
should replace the current framing.

### F1. Phase 1.5 selected the two weakest PVDAQ systems
**Status: OPEN.** Phase 1.5 names `system_51` primary and `system_50` secondary — the weakest
in the set. `system_10` has 6.66 M rows at 0.94–0.99 across fifteen years; `system_4` is
comparable. Both are unused. The likely original reason is the NSRDB Golden weather join, but
the correlation matrix above indicates 10 and 4 sit at essentially the same sky as 51, so the
join should extend to them. **Expanding Tier 1 from two systems to four is close to free** —
confirm against PVDAQ's published lat/lon metadata before relying on it.

## Recommended order

Sequenced by what invalidates what, not by effort.

1. **B1** — rebuild the cluster join. Everything downstream is measured on that table.
2. **A1-c** — decide and build the mechanism by which causal knowledge changes allocation
   (roadmap Phase 2). §6.4's causal-uncertainty ambiguity set is the proposal's own answer.
3. **A2** — materialise the Tier-2 variables and let the engine write them back.
4. **A3 / A4** — settle the orchestrator signature, then write Phase 7.
5. **C1 / C2** — real CVaR scenarios; decouple `V` from `DEMAND_FULFILLMENT_VALUE`.
6. **C4–C7, E1, E2** — counterfactuals, FDR, `tau_max`, the queue, intervention duration.

Narrowable with explicit disclosure rather than built: the edge-tier split, formal regret
bounds, container/VM placement, grid-stability risk. Each is a limitations statement rather
than months of work — but the choice must be deliberate, because §11 currently promises all of
them.

**The one decision that cannot be deferred:** whether to build the event/semantic layer (§6.1)
or rename the contribution. The current implementation is a time-lagged causal graph over
numeric telemetry; the paper calls it an Active Causal Semantic Event Graph.
